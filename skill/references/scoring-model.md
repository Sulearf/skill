# 评分模型与算法口径

## 方案总分

```
总分 = 偏好满足 × w_pref
     + 预算符合 × w_cost
     + 饱腹匹配 × w_full
     + 优惠程度 × w_disc
     + 共享合理 × w_struct
     − 冲突惩罚
```

五项的语义与取值：

| 维度 | 取值 | 口径 |
|---|---|---|
| 偏好满足 `pref` | 0–1 | 每位成员的「主食命中 × 0.5 + 饮料命中 × 0.3 + 口味命中 × 0.2」再对人数取平均；`mainHit` 返回 1（完全命中）/ 0.6（同类）/ 0.3（勉强）/ 0，饮料同理 |
| 预算符合 `cost` | 0–1 | `1 − |花费 − 预算| / 预算`；超出预算时额外乘 0.2 的惩罚系数（即 `s -= 0.8 × 超支比`） |
| 饱腹匹配 `full` | 0–1 | 以 `APPETITE_KCAL` 为目标热量（小 550 / 中 800 / 大 1100 kcal），按偏差比例衰减 |
| 优惠程度 `disc` | 0–1 | `(原价合计 − 现价合计) / 原价合计`，即套餐与促销力度 |
| 共享合理 `struct` | 0–1 | 共享拼盘人均份量与人数、食量的匹配程度 |

**冲突惩罚**（仅在未淘汰的方案上扣分）：

```
penalty = 0.15 × (缺主食人数占比)
        + 0.10 × (缺饮料人数占比)
        + 0.20 × (超个人预算人数占比)
```

> 口径提醒：MCP 的团餐满减（`query-promotions`）在个人点餐场景不可用，因此 `disc` 不使用门店满减规则，改用「原价 vs 现价差额」估算。详见 `references/mcp-integration.md`。

## 三套策略权重

`web/core/engine.js` 顶部 `STRATEGIES`：

| id | 名称 | 侧重 |
|---|---|---|
| `cheap` | 最省钱 | 便宜度 0.45 + 预算符合 0.20 + 优惠 0.15，`cheap` 项专门奖励「人均绝对更低」，避免把「贴近预算」误当成省钱 |
| `balanced` | 最均衡 | 预算符合 0.25 + 偏好 0.35 + 饱腹 0.20 + 共享合理 0.10 |
| `satisfy` | 最满足 | 偏好 0.40 + 优惠 0.17 + 饱腹 0.18 + 预算符合 0.25 |

**注意**：不要把「预算符合」当成「便宜」。历史上曾因缺少独立便宜度项，导致「最省钱」方案反而是三套里最贵的。

## 淘汰规则

- **忌口硬冲突 → 方案直接淘汰**（`eliminated = true`），页面置灰且选择按钮 disabled。
  硬冲突 = 商品的 `diet` 标签命中成员 `avoid`，且该标签**不在** `removable` 里（去不掉）。
- 若冲突标签在 `removable` 里（如酸黄瓜、洋葱），降级为**软冲突**，方案保留并在清单里输出「特调去掉：…」。
- 全员都无候选时进入 `rejected`，页面提示「有 N 位成员的可选搭配受限」，并说明原因。

## 三套方案的差异化

按策略独立打分取各自最优；只有当两套方案的 `signature` 完全相同时，才逐个成员改取次优候选（最多尝试 8 轮）拉开差异。

> 历史坑：早期实现强制每位成员都取不同候选，把「最均衡」方案顶到不合理的价格。**只应在整案重复时做最小扰动。**

## 确认前风险检查（`checkPlan`）

| 级别 | 触发条件 |
|---|---|
| `block` | 商品已售罄/不可售；忌口硬冲突；订单总额超出房间总预算 |
| `warn` | 个人超出预算；缺主食；缺饮料；共享小食份量不足人均 1 份 |
| `info` | 涉及过敏原标签时的官方口径提示；查询失败降级提示 |

售罄项附带替换建议（`suggestReplacement`）：同品类 / 同为套餐、价格与热量最接近、且不违反该成员忌口，最多 3 个。

## AA 分账（`computeAA`）

| 模式 | 口径 |
|---|---|
| `own` 各付各的 | 各自商品自付；共享部分按人数均摊 |
| `even` 完全平摊 | 订单总额 ÷ 人数 |
| `custom` 自定义 | 手动指定每人金额，`normalizeCustom` 负责把差额补到分 |

**金额一律以「分」为单位整数运算**，均摊用最大余额法（`util.allocate`）分配余数，保证：

```
sum(每人应付) === 订单总额
```

页面直接展示该等式结果（`个人金额合计 ✓ 与订单总额一致`），出现不一致时给出差额与「一键摊平差额」。
